(planned, in-progress, or already-shipped work), nothing here is committed to.

## Nearly free — scaffolding already exists, unused

- [x] **Achievements** — done. 24 milestones across progression/first-crafts/orchard/economy/building/time/land in `src/data/achievements.json`, evaluated by the new `AchievementSystem.js` against `ProfileSystem`'s existing (previously-unused) `unlockAchievement()` plumbing. Toast notification + a modal (🏆 button in the HUD) listing all 24 with lock/unlock state. Retroactive: loading a save that already qualifies for milestones credits them immediately instead of waiting for the next matching event. Caught a real ordering bug while building it — `resources.onChange` fires *before* handler-local stat counters (`gameStats.harvests++` etc.) update in the same click handler, so the achievement check needed explicit calls after those counters update, not just a listener on resource changes.
- [ ] **Storage / Cabin upgrades** — `docs/GameDesign.md` §7.2 specs "more tool slots, decorative items, larger production capacity" as a Cabin Upgrade category; never built. Resources also have no storage cap today, which removes a management layer the original design assumed (a Storage Shelves tool is named in `docs/GameDesign.md` §4.1 but doesn't exist in code).

- [ ] **More crops / flavor variants** — in progress. First flavor shipped: **Autumn Hug** (cranberry), see `docs/TODO.md`. Remaining: the multi-crop system (crop-aware `TileGrid`, per-crop `crops.json` entries) has apple/hops/coffee/timber/cranberry; `docs/GameDesign.md` §3.4 still names unused botanical zones (Peach Orchard, Cherry Grove, Blueberry Bend, etc.) and §8.1 still names more cider flavors (Creekside Watermelon, Sticky Paws Apple Caramel, ...) not yet wired to a recipe. - [ ] **Craft Soda line** — non-alcoholic production category speced in `docs/GameDesign.md` §8.7 (Soda Station, botanical-based flavors), unbuilt. Would diversify away from "everything is alcohol," which matters for a family-friendly game.

## Bigger swings

- [ ] **Post-Tier-5 endgame** — progression hard-stops at "Master Roaster" (`progression.json` tier 5). Nothing beyond that today. Worth a prestige mechanic, a Tier 6, or just more deals/recipes to chase once maxed out.
- [ ] **NPC visitors / one-off requests** — dynamic income on top of the existing fixed 14-day distribution-deals system (`deals.json`, `MarketSystem.js`), for more variety than static contracts.
- [ ] **Consumer demand affecting production** (Jim's idea) — sell prices should react to what's actually happening, not just sit flat. Today `MarketSystem.priceMultiplier` is a single global number keyed only to Market level (`levels.json`) and applied uniformly to every item in `store.json` — there's no per-item, per-flavor, or time-based pricing at all, so there's currently zero reason to plan production around demand. Two versions worth considering, smallest first: (1) **seasonal demand** — piggybacks on the not-yet-built Seasonal cycle idea above; a flavor's price climbs during its themed season (Autumn Hug in fall) and softens the rest of the year, giving players a real reason to stockpile cranberries and pre-brew ahead of the spike instead of selling as they go; (2) **supply-pressure demand** — prices soften temporarily on whatever you've been dumping in bulk and recover over time, independent of season, so mass-selling one resource stops being strictly optimal. Either version needs real new state (per-item price history/decay, not just the current flat multiplier) and should probably land after the Seasonal cycle work if going the seasonal route first.
- [ ] **Automated selling** (Jim's idea) — `StoreSystem.sell()` is a single manual action: press a button, the whole stack sells instantly at whatever the current flat price is, no downside to dumping everything at once. An Auto-Sell option — same shape as the existing crafting-station automation (`StoreSystem.toggleAutomation()`, the `auto_bottling`-style upgrades in `upgrades.json`) — would sell off stock gradually over time instead of all at once. This is the natural pair to the demand idea directly above: dump your whole stockpile in one manual sale and eat a price hit from supply pressure, or let Auto-Sell trickle it out steadily near the "fair" price. Without a demand system to react to, automating the sale is just a convenience toggle; the two together are what actually turn selling into an economic decision instead of a reflex.
- [ ] **Spoilage on stored goods** (Jim's idea) — apples (and everything else) sit in inventory forever once harvested/crafted, no decay, no reason not to just hoard indefinitely. Rot already exists as a mechanic today, but only pre-harvest: `ROT_TICKS_NEEDED` (constants.js) flips a ripe, *uncollected* apple tile to `TILE_STATE.ROTTED` after 14 in-game days. `ResourceManager` (resources.js) has no equivalent — once a resource lands in `amounts`, it's a plain number with no age or decay applied, for `fruit` all the way through every crafted/flavored good including the new Autumn Hug line. Jim's suggestion: introduce shelf spoilage at a higher tier, so late-game inventory management actually matters (perishables need selling or processing before they go bad, unlike wood/stone/coins which should stay eternal). Would pair naturally with the not-yet-built Storage Shelves tool (`docs/GameDesign.md` §4.1, same "planned but unbuilt" bucket as the Storage/Cabin upgrades idea above) as the thing that slows or prevents it — spoilage as the problem, Storage Shelves as the upgrade that solves it. Also reinforces the demand/auto-sell ideas directly above: three different reasons to stop treating the shelf as an infinite, static bank.
- [ ] **Cross-device / cloud save sync** (Jim's idea) — came up when Jim asked how his iPad save and his son's save on a separate device would interact. Today there's no interaction at all, by construction: the game is 100% static (GitHub Pages hosting, no backend of any kind), and every profile + save lives entirely in that one browser's own `localStorage` (`ProfileSystem.js`, save data under `hbco_save_<profileId>_<slot>`). That's actually why two family members on two devices already just works with zero setup — separate devices means separate storage, no possible collision — but the flip side is there's no way to continue *the same* save from a second device, and clearing site data or going incognito loses everything with no backup anywhere. This is a different tier of work than everything else on this list: every other item is frontend-only, buildable as static code shipped to GitHub Pages as-is. Real sync needs actual new infrastructure — some form of account/identity (even something lightweight, like a short sync code rather than a full login) plus a real backend to store and serve profile/save JSON, since GitHub Pages can't run server logic itself. Worth scoping as its own project, not a quick add.
