## Orchard & Land

  - East zone → Tier 1, North → Tier 2, West → Tier 3, South → Tier 4
  - Permanent treeline dividers separate zones visually
- [x] **Purchasable outposts (Option B)** — 200 🪙 (Market, Tier 2+) buys a placement: the game switches to the Orchard and the next tile tap tries to drop a 3×3 clearable cluster there. Hit a real design conflict while building this: the existing 10×10 map has *zero* contiguous 3×3-locked area anywhere, at any tier — every named zone (`ZONE_DEFS` in tiles.js) is only 2 tiles thick, by design, so a literal "3×3 anywhere on the locked grid" could never succeed. Resolved per direction from Jim: the grid itself now grows +2 rows/cols on the bottom-right for every tier reached (`GRID_GROWTH_PER_TIER` in constants.js, `TileGrid.resize()` in tiles.js — existing coordinates never shift, so old saves restore correctly into the bigger grid), so there's always fresh open frontier for outposts to land in. Bonus: normal tile-clearing now also organically bleeds into the new frontier via the existing adjacency-unlock, not just outposts.
- [x] **Outpost tiles unclickable after opening the board** — reported: buying an outpost switched to the Orchard as expected, but tapping a tile to place it did nothing. Root cause was a classic flexbox trap: `#orchard-container` had `overflow-x: auto` to let the grown (tier-growth) grid scroll into view, but flex items default to `min-width: auto`, which stopped it from ever shrinking below the grid's intrinsic width — so its own scrollbar never activated, and the oversized grid got silently clipped by the ancestor `#game-area`'s `overflow: hidden` with no way to reach the clipped tiles. A direct JS `.click()` on the clipped element still worked (proving the placement logic itself was fine), but real pointer clicks landed outside the actual paint/hit-test area. Fixed by adding `min-width: 0` to both `.scene` and `#orchard-container` in style.css. Verified with a fresh tier-2 save: bought an outpost, and a real pixel-coordinate click on a locked frontier tile now correctly places it ("🏕️ New outpost claimed!").
- [x] **No valid outpost placement exists after normal play** — follow-up report from Jim: "theres no valid placement the way it is now," expecting outposts to extend the board boundary rather than open a pocket within it. Investigated with a Node simulation of the real `TileGrid` logic (clear every reachable tile via adjacency, same as normal play, then grow to tier 2 and search for any valid 3×3 spot) — confirmed **zero valid spots exist anywhere**, reproducibly, not just in Jim's specific save. Root cause: the tier-growth frontier (`GRID_GROWTH_PER_TIER = 2`) is only 2 tiles thick, and the "bonus" adjacency-bleed added alongside the original outpost fix (tile-clearing organically unlocking into fresh frontier) erodes that 2-tile band from the inside the moment a player clears anything bordering it — a 2-wide band can never hold a 3×3 all-locked block once its inner edge is touched, which happens naturally during ordinary play. First fix attempt (superseded below): added a `frontier` flag to `Tile`, excluded from `_unlockNeighbors()`'s adjacency auto-unlock, guaranteeing a reserved pocket always existed.
- [x] **Outposts redesigned to actually grow the board, not unlock a pocket** — Jim clarified the original intent: "the original idea was to grow the board, not just unlock tiles. this helps with game longevity." The 3×3-pocket mechanic (however reliable after the fix above) was never the goal — outposts were meant to be a repeatable, player-directed way to extend the board's actual boundary, independent of tier progression. Redesigned per Jim's choice of "tap an edge to pick a direction" over "auto-grow with no tap": `TileGrid` now tracks `cols`/`rows` independently instead of a single square `size`, with `growRight(amount)`/`growBottom(amount)` growing one edge at a time (existing coordinates still never shift, so saves stay valid) — `resize(newSize)` becomes a thin wrapper over both, used only by tier progression which still grows both edges together. Scoped growth to the right/bottom edges only (not full 4-directional) since top/left growth would require shifting every existing tile coordinate and remapping `ZONE_DEFS`/gap-tile dividers, a much larger and riskier change than the ask called for. Outpost purchase now enters the same placement mode as before, but tapping a tile on the right or bottom edge (highlighted with a pulsing cyan glow, `.tile-grow-target` in style.css) extends that edge by `OUTPOST_GROWTH_AMOUNT` (3) fresh LOCKED tiles; tapping the interior shows a warning instead. Removed the now-obsolete `canPlaceOutpost`/`placeOutpost` pocket logic entirely. Updated the outpost's Market description, purchase message, and How-to-Play guide text to match. Added `MAX_GRID_DIMENSION` (30) as a sanity cap on each axis. Since the board can now grow asymmetrically (e.g. wider than tall), `main.js`'s restore flow grows the live grid to match the *saved* tiles array's actual shape (not just the tier-baseline square) before restoring tile state, so outpost-driven growth isn't dropped on reload. Verified live: bought outposts and tapped both a real bottom-edge tile (grew rows only, "orchard grows south!") and a right-edge tile (grew columns only, "grows east!"), confirmed an interior tap is rejected with a warning, and confirmed the resulting asymmetric grid (17 cols × 14 rows) survives a full page reload after a real autosave.
- [x] **Newly-grown land was permanently locked forever** — follow-up report from Jim right after the redesign above: "i expanded the board but theyre all locked. if i expand shouldnt they be available to develop." Real regression: the `frontier` flag from the earlier (superseded) fix was still being set on every tile `growRight()`/`growBottom()` created, and `_unlockNeighbors()` still excluded `frontier` tiles from adjacency auto-unlock — a guard that made sense when outposts *reserved* a pocket from erosion, but which now had no purpose and instead permanently trapped every freshly-grown tile in LOCKED with no path out, since nothing else ever unlocks a frontier tile. Removed the `frontier` flag entirely (from `Tile`, `_unlockNeighbors()`, `snapshot()`/`restore()`). First attempt (superseded below) only auto-unlocked the border row/column if it happened to sit next to ground the player had already cleared — too conservative: on a fresh expansion the bordering edge is usually still locked too, so nothing opened and it looked exactly like the original bug.
- [x] **Grown land still looked locked — round 2** — Jim reported the same symptom again right after the fix above ("the new outpost tiles are still locked when i create them"), which correctly pointed at that conservative seam-only logic. This is a paid, player-directed expansion — the right bar isn't "eventually openable like the rest of the map," it's "usable now." `growRight()`/`growBottom()` now create every new tile straight into `CLEARABLE` instead of `LOCKED`, no conditions. Since `resize()` (tier progression) is built on the same two methods, tier-based grid growth gets the same treatment, which is actually *more* consistent with the rest of the game — every other tier-unlocked zone (`unlockZone()`) has always opened in bulk, not progressively. Verified with a Node simulation against the live `TileGrid` code (every tile in a fresh `growBottom(3)`/`growRight(3)` comes back `clearable`) and live in-browser: bought an outpost, grew both edges, and every new tile rendered as a normal leafy clearable tile immediately, with zero locked tiles left anywhere except the legitimately-still-unpurchased West zone and Hop Fields zone.
- [x] **Pay-to-unlock-early** — Jim's request: "give them a way to use coins to unlock tiles early," as an alternative to waiting on tier/adjacency progression or buying a whole zone/outpost. Confirmed with Jim it should bypass tier and zone-purchase gating entirely (e.g. unlock one West-zone tile before Tier 3, or one Coffee Grove tile without buying the zone), not just apply within already-reached areas. Added `ACTION.UNLOCK` (new, `UNLOCK_TILE_COST` = 40 🪙 in constants.js) valid only on `LOCKED` non-permanent tiles — `TileGrid.performAction()` flips the single tapped tile straight to `CLEARABLE` with no cascade to neighbors (unlike `CLEAR`'s adjacency unlock). Priced deliberately above every zone's effective per-tile price (Hop Fields ~17.5🪙/tile, Coffee Grove 35🪙/tile) so buying the whole zone or an Outpost always stays the better deal — this is a premium "I want *this one tile* right now" option, not a way to undercut the zone economy. Surfaced in the existing tile action menu (`ui/menus.js`) via the same generic afford/spend flow every other tile action already uses, so the button auto-disables when short on coins. Permanent forest-divider tiles are untouched (still show the "Ancient Forest" message, no unlock option). Verified live: tapped a locked West-zone tile at Tier 1, paid 40🪙 (500→460), tile flipped to clearable immediately with neighbors still locked; permanent divider tiles unaffected.
- [x] **Multi-crop planting** — crop selection UI on Plant, tile `cropType` tracking, tier-gated availability (per `crops.json` `unlockTier`), harvest yields pulled from crop data. Fixed a bootstrap bug along the way: hops/coffee `plantCost` consumed the same resource they produce, so first-ever planting was impossible — a starter seed grant now fires on tier unlock (mirrors the existing `bottles:3` starter fix for the cider chain). Also fixed hops' `unlockTier` (was 3, didn't match when `hops_crop` actually unlocks at tier 4).
- [x] **Forest tile** — timber trees were already a renewable-wood mechanic but lived as a hardcoded parallel system (`ACTION.PLANT_TREE`, `cropType === 'timber'` special-cases scattered across tiles.js/menus.js/main.js) alongside the new crops.json-driven planting. ## Production & Crafting

- [x] Press timer (12s), Ferment requires 3 juice → 1 cider (90s), Bottle requires 3 cider → 3 bottles (20s). Caught a real bug from an earlier balance pass: `ferment_cider` was quietly also outputting a free bottle (propping up its own economics, since 3 juice → 1 cider alone is a loss at store prices), which meant `bottle_cider`'s "3 cider + 1 bottle → 1 bottle" was a dead step — net zero bottles gained, players had no reason to ever use the Bottling Station. Removed the bonus bottle from fermenting and gave bottling a real 1:1 cider→bottle yield, so it's the step that actually produces bottles now (+55% margin). Also reverted the `bottles: 3` starting stock (`resources.js`) — it was only ever a workaround for the old self-referential recipe and was trivializing the "reach 3 bottles" Market-unlock gate by starting past it.

## Save & Persistence

- [x] **Save/Load** — `ResourceManager`, `TileGrid`, and `ConstructionSystem` all have `snapshot()`/`restore()`; autosaves to localStorage on each new day; restores resources, tiles, tool states, tier, first-crafts, and market unlock on load. In-progress crafting timers *are* saved and re-armed on load (fixed a stale note here claiming otherwise — `CraftingSystem.restore()` already re-arms `setTimeout`s for unexpired timers and finishes expired ones immediately).
- [x] **No top-level "Continue" on the main menu** — Jim's report: after quitting and reopening, there's no way to resume a game without going through Profiles first; he asked for top-level access. Root cause: a "Continue" button already existed in `renderMainMenu()`, gated on `ProfileSystem.getSelectedProfile()` — but `boot()` never actually selected anyone at startup (`_selectedProfile` is a pure in-memory field with no persisted "last active profile" pointer anywhere), so that condition was always false on a fresh load and the button never appeared; the only way to reach a profile was the explicit Profiles screen. Also found "Continue" and "Load Game" were wired to the exact same handler (`showSaveSelect`), so even once reachable neither was a real one-tap resume. Fixed both: `boot()` now auto-selects whichever saved profile has the most recent `lastPlayed` timestamp before rendering the main menu, and "Continue" now calls `SaveSystem.getMostRecentSave()` (previously a dead/unused method) to jump straight into that profile's most recently played save, falling back to the slot picker only if the profile has no save yet. "Load Game" still opens the slot picker unchanged, for picking a different save or managing slots. Verified live: a fresh page load now shows "Continue" as the primary button with a "Playing as ⟨name⟩" badge, and clicking it goes directly into gameplay at the exact saved day/tier/coins with zero extra taps; reloading again and using "Load Game" instead still correctly shows the Orchard 1/2/3 picker.
- [x] **Hardening pass** — found and fixed a real stored-XSS gap: the player-name field (the game's only free-text input) was interpolated unescaped into `innerHTML` on the Profile Select and Choose Your Orchard screens, so a name like `<img src=x onerror=...>` would execute as markup. Added an `escapeHtml()` helper and applied it everywhere `playerName` renders. Also fixed: deleting a profile never removed its `hbco_save_*` localStorage entries — they became permanently orphaned since the profile id is unreachable once deleted; and `CraftingSystem.restore()` matched a running craft back to its recipe by scanning for *any* recipe on that station, which only worked by coincidence (every station currently has exactly one recipe) — now the actual `recipeId` is saved alongside the timer so restore can't silently apply the wrong recipe's output if a station ever gets a second recipe.
