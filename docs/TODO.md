- [x] **Couldn't clear (decommission) a mine shaft with Auto Mode on** — Jim: "i cant clear a mine." Real race condition, not a UI bug: with Auto Mode + Harvest Bell active (i.e. most players who've automated anything), `main.js`'s tick loop called `tileGrid.autoMine()` 600ms after every tick, which unconditionally restarts mining on *every* currently-`MINE_SHAFT` tile with no way to exempt one. Since a mine only ever becomes `MINE_SHAFT` for that same 600ms window before the next auto-restart claims it, there was no realistic way to tap the tile, get the menu, and click "Fill In" before it flipped back to `MINING` (where `CLEAR` isn't a valid action at all) — effectively never, since selecting an option from a freshly-opened menu alone typically takes longer than 600ms. Fixed two ways: (1) reordered the tick so `autoMine()` runs *before* `completeMines()` instead of 600ms after — a mine that finishes this tick isn't swept until the *next* tick, giving it a full ~3s of stable visibility instead of ~600ms; (2) added a `skipTile` param to `TileGrid.autoMine()`, wired to `actionMenu.currentTile` — whatever tile the action menu is currently open on is now completely exempt from the sweep, so once you've got the menu open, "Fill In" is guaranteed to work no matter how long you take to click it, not just lucky timing. Verified both: a Node-level test confirms the excluded tile survives a sweep untouched while every other mine_shaft tile still gets swept normally (no regression to the intended "hands-off automation" behavior); live in-browser, opened the menu on a freshly-completed mine shaft, deliberately waited 8+ seconds (multiple tick cycles that would've broken it under the old code) before clicking Fill In, and it correctly decommissioned the tile back to Cleared.

Fixed by adding `min-width: 0` to both `.scene` and `#orchard-container` in style.css. Verified with a fresh tier-2 save: bought an outpost, and a real pixel-coordinate click on a locked frontier tile now correctly places it ("🏕️ New outpost claimed!").

- [x] **Outposts redesigned to actually grow the board, not unlock a pocket** — Jim clarified the original intent: "the original idea was to grow the board, not just unlock tiles. this helps with game longevity." ## Market & Economy

- [x] **Demand pricing + shelf spoilage + Auto-Sell, shipped as one bundle** — Jim raised a real problem: once every crafting station is automated (`auto_press`/`auto_bottling`/etc. plus Harvest Bell's auto-water/mine/harvest), there's nothing left to actually *do* except periodically hit Sell. All three unlock together at `ECONOMY_PRESSURE_UNLOCK_TIER = 3` (`constants.js`) — deliberately the same tier, so demand pricing (which makes dump-selling costly) never appears without Auto-Sell (the tool that avoids dump-selling) already purchasable.
  - **Supply-pressure demand** (`MarketSystem.js`): each sale nudges that specific item's own price down (`DEMAND_DROP_PER_UNIT_SOLD = 1%` of base price per unit sold in one sale), floored at 50% of base (`DEMAND_MIN_MULTIPLIER`), recovering 5 percentage points/day (`DEMAND_RECOVERY_PER_DAY`) via the existing `onNewDay` hook. Multiplies on top of the existing market-level `priceMultiplier`, doesn't replace it. Deliberately scoped to supply-pressure only, not the seasonal half of Jim's original idea — that depends on the not-yet-built Seasonal Cycle and would've blocked this whole bundle on a second unbuilt system.
  - **Shelf spoilage** (`SpoilageSystem.js`, new): raw harvested crops only (`PERISHABLE_RESOURCES` = fruit, cranberry, blueberry, hops, coffee_bean) — crafted/bottled goods stay eternal. Approximates per-batch freshness with one "since empty" timestamp per resource type (`ResourceManager.sinceEmptyTick()`, new) rather than true per-unit aging, which would've meant rearchitecting every system that touches resources from a flat `{type: number}` map to per-batch records — the timestamp only resets on the empty→nonzero transition, not on every top-up, so topping off a stale pile with one fresh harvest doesn't "refresh" the whole pile. A pile spoils 10 days after it was last empty (`SHELF_ROT_TICKS_NEEDED`), losing 5% of current stock per tick once spoiling starts. Mirrors the existing pre-harvest apple-rot mechanic (`ROT_TICKS_NEEDED`) as its sibling for *stored* goods instead of tile-bound crops.
  - **Auto-Sell** (`StoreSystem.js` + `upgrades.json`'s new `auto_sell`/"Market Broker" entry, 400🪙): just another `type: 'automation'` upgrade, same shape as every crafting-station automation — the existing purchase/pause-resume UI in the Market's Automation section picked it up for free with zero new code. Once purchased, trickles 50% of the stock sitting above a per-item reserve threshold (`AUTO_SELL_TRICKLE_PCT`, new "Keep at least" input on every sell card) once per day, rather than dumping the whole excess at once — approaches the reserve asymptotically, which is what actually makes it pair with demand pricing: a manual Sell All tanks that item's price, trickling doesn't.
  - Verified two ways: (1) a 25-assertion Node simulation against the real source files (spoilage timing at the exact tick threshold, non-perishables never spoiling, emptying-and-refilling correctly resetting the clock, demand drop/floor/recovery math, tier-gating, auto-sell trickle/pause/reserve behavior, full save/restore round-trip for every new field) — all 25 passed; (2) live in-browser end-to-end: sold a real 60-apple dump and watched the price correctly show "(-50% oversold)" floored at the minimum, purchased Market Broker and watched it correctly appear via the existing automation-card pattern, and caught a *real* overnight auto-sell run live (Wood 50→25, Stone 50→25, Cranberries 40→20, all ~50% trickled exactly as designed, coins +110) during an unrelated wait in testing — the day-boundary hook, trickle math, and demand-recording all fired correctly together, unprompted, on real game state.

## Save & Persistence

- [x] **Save/Load** — `ResourceManager`, `TileGrid`, and `ConstructionSystem` all have `snapshot()`/`restore()`; autosaves to localStorage on each new day; restores resources, tiles, tool states, tier, first-crafts, and market unlock on load. In-progress crafting timers *are* saved and re-armed on load (fixed a stale note here claiming otherwise — `CraftingSystem.restore()` already re-arms `setTimeout`s for unexpired timers and finishes expired ones immediately).
- [x] **No top-level "Continue" on the main menu** — Jim's report: after quitting and reopening, there's no way to resume a game without going through Profiles first; he asked for top-level access. Root cause: a "Continue" button already existed in `renderMainMenu()`, gated on `ProfileSystem.getSelectedProfile()` — but `boot()` never actually selected anyone at startup (`_selectedProfile` is a pure in-memory field with no persisted "last active profile" pointer anywhere), so that condition was always false on a fresh load and the button never appeared; the only way to reach a profile was the explicit Profiles screen. Also found "Continue" and "Load Game" were wired to the exact same handler (`showSaveSelect`), so even once reachable neither was a real one-tap resume. Fixed both: `boot()` now auto-selects whichever saved profile has the most recent `lastPlayed` timestamp before rendering the main menu, and "Continue" now calls `SaveSystem.getMostRecentSave()` (previously a dead/unused method) to jump straight into that profile's most recently played save, falling back to the slot picker only if the profile has no save yet. "Load Game" still opens the slot picker unchanged, for picking a different save or managing slots. Verified live: a fresh page load now shows "Continue" as the primary button with a "Playing as ⟨name⟩" badge, and clicking it goes directly into gameplay at the exact saved day/tier/coins with zero extra taps; reloading again and using "Load Game" instead still correctly shows the Orchard 1/2/3 picker.
- [x] **Hardening pass** — found and fixed a real stored-XSS gap: the player-name field (the game's only free-text input) was interpolated unescaped into `innerHTML` on the Profile Select and Choose Your Orchard screens, so a name like `<img src=x onerror=...>` would execute as markup. Added an `escapeHtml()` helper and applied it everywhere `playerName` renders. Also fixed: deleting a profile never removed its `hbco_save_*` localStorage entries — they became permanently orphaned since the profile id is unreachable once deleted; and `CraftingSystem.restore()` matched a running craft back to its recipe by scanning for *any* recipe on that station, which only worked by coincidence (every station currently has exactly one recipe) — now the actual `recipeId` is saved alongside the timer so restore can't silently apply the wrong recipe's output if a station ever gets a second recipe.
- [x] **Manual backup/restore to a file** — Jim asked whether progress could be saved to a local file (autosave already exists, but it's localStorage-only — clearing site data or switching browsers loses everything with no recovery). New `src/systems/BackupSystem.js`: `exportBackup()` bundles every `hbco_*` localStorage key (all profiles + all saves) into one timestamped JSON file; `importBackup(file)` validates and restores it, overwriting matching keys. On whether the user can pick the save location: it's split by platform, not a single yes/no. Desktop Chrome/Edge get a real native "Save As" dialog via `showSaveFilePicker()` (File System Access API) — full folder+filename control. That API doesn't exist in Safari/WebKit at all, so on Jim's actual device (iOS PWA) there's no in-page picker; export falls back to a standard `<a download>` + Blob, which iOS itself intercepts as a Share Sheet / "Save to Files" flow — the user still picks a folder, just through iOS's own UI rather than the web app's. True silent autosave-to-file isn't possible on iOS either way (no background file-write API, and browsers require a real user gesture before any download), so this stays a manual, button-triggered action, wired into Settings → **Data & Backup** (`renderSettings()` in main.js) alongside the existing Audio/Gameplay/Accessibility sections. Restore requires an explicit confirm() before it overwrites anything, then reloads the page so every system re-initializes from the restored data. Verified in-browser: exported through the no-picker fallback path and confirmed the correct filename/blob triggers; round-tripped a crafted backup file through `importBackup()` after clearing all `hbco_*` keys and confirmed byte-identical restoration; confirmed both malformed-JSON and non-backup JSON files are rejected with a clear message instead of corrupting storage.
